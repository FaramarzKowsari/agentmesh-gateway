# Execution Plan: OpenAI Responses API

Status: completed for the v0.2.0 verified surface

## Objective

Expose a protocol-neutral Responses boundary that can serve coding-agent clients while preserving provider independence, explicit semantic limits, and deterministic compatibility tests.

## Completed work packages

1. Text input normalization for Responses messages and instructions.
2. Deterministic parser/renderer fixtures for text requests.
3. `/v1/responses` non-streaming route.
4. Ordered text SSE lifecycle with strict sequence tests.
5. Non-streaming function-call and function-output normalization across Responses, Chat Completions, and Anthropic Messages.
6. Cross-vendor function-tool schema translation where an explicit custom-function mapping exists.
7. Codex custom-provider contract fixture using the `wire_api = "responses"` boundary and a local fake upstream.
8. Streaming failover guard: retry before first committed output, never silently switch providers after commitment.
9. Streaming function-call argument normalization from OpenAI-compatible and Anthropic upstreams.
10. Responses `response.function_call_arguments.delta` / `.done` rendering plus function-call output-item lifecycle.
11. Codex contract coverage for a streamed function call followed by `function_call_output` continuation.
12. Failover safety after the first streamed function-call delta.
13. Explicit ingress feature gates for unsupported Responses input items and unknown tool types.
14. Native `responses` upstream adapter for semantics that must not be downgraded.
15. Request-side preservation of reasoning controls, reasoning input items, include fields, prompt-cache/service-tier controls, text controls, stream options, client metadata, tool choice, parallel-tool-call policy, and store policy.
16. Native Responses SSE passthrough so reasoning items and encrypted reasoning content survive the gateway boundary.
17. Capability-aware routing that excludes non-native providers when a request requires native Responses semantics.
18. Deterministic Codex-style reasoning contract with a fake native upstream and no live API key.
19. Explicit whitelist for the recognized public Responses tool-type surface used by v0.2.
20. Native-only routing for recognized non-function Responses tools while retaining cross-protocol translation for custom `function` tools.
21. Byte-semantic JSON preservation of native tool definitions through the native Responses adapter.
22. Native built-in-tool SSE lifecycle passthrough, including deterministic web-search event coverage.
23. Preflight provider eligibility before streaming headers are committed.
24. Release smoke checks for package version, CLI version, health version, and a local ASGI route with no provider network call.
25. Security alignment so `/admin/providers` follows configured bearer authentication.
26. Release documentation that distinguishes translated compatibility from native preservation and records explicit limits.

## Deferred compatibility backlog

The following items are outside the advertised v0.2.0 surface and therefore do not block completion of this plan:

1. Cross-vendor reasoning translation between Responses, Chat Completions, and Anthropic thinking formats.
2. Cross-vendor translation or local execution of Responses-native built-in tools.
3. Websocket Responses sampling.
4. Image/audio normalization across protocols and additional non-text input/output items.
5. Complete prompt-cache semantic translation across vendors.
6. Codex authentication modes, compaction, memory, multi-agent behavior, and exhaustive CLI/SDK coverage.
7. Additional Claude Code-compatible, Cline, and OpenCode contract suites.
8. Per-client model aliases and other client-specific policy conveniences.

## Acceptance gates

- [x] no live API key in default tests
- [x] existing Chat Completions and Messages tests remain part of CI
- [x] event ordering covered by deterministic fixtures
- [x] provider failures before stream commitment can fall back; failures after commitment cannot silently switch providers
- [x] Codex public custom-provider boundary covered by deterministic text, custom-tool-loop, native reasoning, and native-tool contracts
- [x] incomplete semantics are documented rather than simulated
- [x] release version is consistent across package/runtime/CLI/health smoke tests
- [x] CI is configured for Python 3.11, 3.12, and 3.13

The final release gate is the pull-request CI run for the v0.2.0 release branch. If that run is green on all matrix versions, the implementation and the advertised compatibility surface are aligned for v0.2.0.
