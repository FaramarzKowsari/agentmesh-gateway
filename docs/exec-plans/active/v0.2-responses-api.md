# Execution Plan: OpenAI Responses API

Status: active

## Objective

Expose a protocol-neutral Responses boundary that can serve coding-agent clients while preserving provider independence, explicit semantic limits, and deterministic compatibility tests.

## Completed work packages

1. Text input normalization for Responses messages and instructions.
2. Deterministic parser/renderer fixtures for text requests.
3. `/v1/responses` non-streaming route.
4. Ordered text SSE lifecycle with strict sequence tests.
5. Non-streaming function-call and function-output normalization across Responses, Chat Completions, and Anthropic Messages.
6. Cross-vendor function-tool schema translation for non-streaming calls.
7. Codex custom-provider contract fixture using the current `wire_api = "responses"` boundary and a local fake upstream.
8. Streaming failover guard: retry before first committed output, never silently switch providers after commit.
9. Streaming function-call argument normalization from OpenAI-compatible and Anthropic upstreams.
10. Responses `response.function_call_arguments.delta` / `.done` event rendering plus function-call output-item lifecycle.
11. Codex contract coverage for a streamed function call followed by `function_call_output` continuation.
12. Failover safety after the first streamed function-call delta.
13. Explicit ingress feature gates for unsupported Responses input items and built-in tools.
14. Native `responses` upstream adapter for semantics that must not be downgraded.
15. Request-side preservation of reasoning controls, reasoning input items, include fields, prompt-cache/service-tier controls, text controls, stream options, client metadata, tool choice, parallel-tool-call policy, and store policy.
16. Native Responses SSE passthrough so reasoning items and encrypted reasoning content survive the gateway boundary.
17. Capability-aware routing that excludes non-native providers when a request requires native Responses semantics.
18. Deterministic Codex-style reasoning contract with a fake native upstream and no live API key.

## Remaining work packages

1. Define an explicit cross-vendor reasoning policy rather than attempting implicit Responses-to-Anthropic or Responses-to-Chat translation.
2. Add explicit gates and/or native support for built-in tools, websocket sampling, images/audio, and other non-text Responses items.
3. Define authentication-mode compatibility separately from sampling-protocol compatibility.
4. Cover Codex compaction and memory endpoints only if they become part of the advertised product surface.
5. Add additional coding-client contract suites only when their public wire boundaries can be tested deterministically.
6. Move the plan to completed only when the advertised v0.2 compatibility surface matches `docs/product-specs/compatibility.md`.

## Acceptance gates

- no live API key in default tests
- all existing Chat Completions and Messages tests remain green
- event ordering covered by fixtures
- provider failures before stream commit can fall back; failures after commit cannot
- current Codex public custom-provider boundary covered by deterministic text, tool-loop, and native reasoning contracts
- incomplete semantics are documented rather than simulated
- CI green on Python 3.11, 3.12, and 3.13
